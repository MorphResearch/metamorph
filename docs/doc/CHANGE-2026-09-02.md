# Sensenova 接入 + 前端流式与 TRAE 风格改版记录

**日期**: 2026-09-02
**范围**: 模型供应商配置、旧库迁移修复、回答流式输出、前端全面改版

## 背景与问题清单

| # | 问题 | 根因 |
|---|------|------|
| 1 | 切换 sensenova 供应商后启动失败 / 模型 404 | 默认 provider 是 deepseek；"SenseNova 6.8 Flash Lite" 是产品显示名，API 需要 `sensenova-6.8-flash-lite` |
| 2 | 前端全面报 "提交失败: Failed to fetch"、"加载失败" | `.metamorph/runs.db` 是旧 schema，`runs` 表缺 `conversation_id` 列，所有查库接口抛 `sqlite3.OperationalError` 导致连接中断 |
| 3 | "思考"与回答内容重复 | 前端把 `model.decision.summary`（回答前 200 字）渲染成"思考"卡片；sensenova-6.8-flash-lite 非推理模型，无真实 `reasoning` 输出 |
| 4 | 回答不是流式 | 回答内容只在内存累积、完成后一次性落库，前端 1.5s 轮询看不到过程 |
| 5 | 整页跟着滚动 | grid/flex 子项默认 `min-height: auto`，内容撑破 100vh 导致整页滚动条 |
| 6 | 前端样式与主流产品差距大 / 改版后不生效 | 旧视觉风格；`static_file` 未发 `Cache-Control` 头，浏览器启发式缓存旧 CSS/JS |

## 修改文件清单

### 1. `llm/providers.py` — sensenova 模型配置

```python
"sensenova": {
    "model": "sensenova-6.8-flash-lite",   # API 模型 ID，非显示名
    "base_url": "https://token.sensenova.cn/v1",
    "api_key_env": "SENSENOVA_API_KEY",    # 环境变量名，key 本身不落盘
},
```

**注意**: 启动时必须同时提供 key 与 provider：

```powershell
$env:SENSENOVA_API_KEY="sk-xxx"
python main.py serve --port 8787 --provider sensenova
```

### 2. `state/store.py` — 旧库 schema 自动迁移

新增 `_migrate_schema()`，在 `_initialize()` 末尾调用：

- 用 `PRAGMA table_info(runs)` 检测旧表缺 `conversation_id` 列
- `ALTER TABLE runs ADD COLUMN conversation_id TEXT NOT NULL DEFAULT ''`
- 回填 `UPDATE runs SET conversation_id = run_id`（每条旧记录成为独立对话，历史数据保留）

修复效果：`/v1/conversations`、`/v1/tasks` 等接口恢复 200，前端不再 "Failed to fetch"。

### 3. `graphs/loop.py` — 回答流式事件 `answer.delta`

与 `reasoning` 事件同模式，content chunk 实时落盘（streaming 与非流式回退两条路径都覆盖）：

```python
if chunk.content:
    assistant_content += chunk.content
    logger.emit("answer.delta", step=turn, text=chunk.content)
    if emit:
        emit("answer.delta", {"text": chunk.content, "step": turn})
```

前端轮询 `/v1/runs/{id}/events` 读到增量事件即可渲染打字机效果。`model.decision.summary` 字段保留（证据日志不变），仅前端不再用它当"思考"展示。

### 4. `api/middleware.py` — 静态资源缓存头

`static_file()` 响应增加：

```python
handler.send_header("Cache-Control", "no-cache")
```

之前无缓存头导致浏览器长期使用旧 CSS/JS（改版后用户看到的仍是旧界面）。`no-cache` 为协商缓存，本地文件服务开销可忽略，保证前端改动刷新即生效。

### 5. `api/frontend/app.js` — 渲染逻辑重构

核心变化在 `renderEventsInto()`（跨事件维护流式缓冲）：

| 事件 | 处理 |
|------|------|
| `reasoning`（有真实文本时） | 渲染"✦ 深度思考"折叠面板，增量追加；无 reasoning 则面板完全不出现（思考与回答不再重复） |
| `answer.delta` | 累积到回答区，`trim()` 后展示（模型回答常以 `\n` 开头，pre-wrap 下会产生顶部空行）；配合 400ms 轮询形成打字机效果 |
| `model.decision` + `action=tool_call` | 该轮流出的文本 `trim()` 后归档为"第 N 步"卡片（纯空白叙述不渲染卡片），回答区清空等待最终答案 |
| `model.decision` + `action=finish` | 不渲染卡片（回答本身即结果） |

其他调整：

- `addAssistantMessage`：结构改为 `avatar + msg-col(ai-name + status-line + chain + final-answer)`，AI 回复去气泡平铺
- `addUserMessage`：浅灰气泡 + 下方时间戳（`msg-time`）
- `finishMessage`：完成后思考面板自动折叠、消息加 `done` 类（光标消失）、移除顶部状态行、隐藏空的 chain 容器、底部仅保留状态 pill（不显示模型名/会话 ID）
- 轮询间隔 1500ms → **400ms**（流式观感的关键参数）
- 历史列表条目只渲染单行标题（`h-task`），不再显示任务数 / 会话 ID / 预览

### 6. `api/frontend/styles.css` — TRAE 风格全面改版

- 配色体系：灰白极简（`--bg: #f7f7f8`、`--accent: #4d6bfe`），替换原蓝紫渐变
- AI 消息无气泡平铺；用户消息浅灰气泡（`#e9e9ec`）
- 滚动布局：`html/body overflow:hidden` + `.app grid-template-rows: minmax(0, 100vh)` + 各滚动容器 `min-height: 0` —— 整页不滚动，只有左侧历史列表和右侧消息区内部滚动，header/composer 固定
- 输入区：白底大圆角卡片 + 圆形蓝色 ↑ 发送按钮（`index.html` 按钮文字同步改为 `↑`）
- 思考面板/工具卡/摘要卡统一中性灰调细边框
- 打字机光标：`.answer-body:not(:empty)::after`，仅运行中且有内容时闪烁
- 历史列表：紧凑单行（padding 8px、间距 1px、单行省略号）
- 侧边栏：与主区同底色菜单风，"新建对话"为菜单项（注意：按钮文字自带 `+`，CSS 不要再加 `::before` 伪元素加号，曾出现双加号）

## 已知边界

- 轮询模式下流式采样频率受间隔限制：400ms 下短回答（1-2s 完成）只能采到 2-5 帧，长回答效果明显；如需真正逐 token 推送需升级为 SSE/WebSocket
- sensenova-6.8-flash-lite 无 reasoning 输出，思考面板正常情况下不出现；换用推理模型（如 deepseek-r 系列）会自动显示真实思考链
- API key 仅存在于服务进程环境变量，进程重启后需重新设置（或 `setx SENSENOVA_API_KEY "sk-xxx"` 持久化到用户环境变量）

```powershell

# 2. 健康检查

# 3. 流式事件检查：提交任务后观察
```

# 工作区文件访问 + 文件夹上传功能

**日期**: 2026-09-02
**范围**: Agent 工具层（写入/列目录）、`read_document` 扩展、文件夹上传 API、前端上传交互

## 背景与问题清单

| # | 问题 | 根因 |
|---|------|------|
| 1 | Agent 只能"读"，无法把整理结果落盘成文件 | 工具层只有 `read_document`，没有写文件工具 |
| 2 | 模型无法枚举工作区内容，不知道上传文件夹里有什么 | 没有列目录工具，`read_document` 只能按已知路径读 |
| 3 | 上传的 `.py/.js/.yaml` 等代码配置文件读不了 | `read_document` 白名单只有 txt/md/json/csv/log |
| 4 | 用户只能上传图片（≤6 张），无法上传整个文件夹 | `/v1/uploads` 只收图片扩展名且 uuid 重命名会破坏目录结构 |

## 修改文件清单

### 1. `tools/fileops.py`（新增）— `write_file` 与 `list_files` 工具

- `write_file(path, content)`：工作区内 UTF-8 覆盖写入，自动建父目录；注册时 `mutates=True`，受 `METAMORPH_ALLOW_WRITE` 执行策略守门（默认只读时 dispatch 直接拒绝）
- `list_files(path, pattern, recursive)`：列目录结构（带文件大小），支持通配符过滤与递归；扫描上限 2000 条、返回上限 500 条（防 node_modules 级巨型目录撑爆 tool 结果）
- 两个工具共享 `_resolve_within_workspace()`：`resolve()` 消解 `..`/符号链接后 `relative_to()` 判定，任何工作区外路径直接拒绝（信任边界统一）

### 2. `tools/document.py` — `read_document` 文本白名单扩展

`_TEXT_SUFFIXES` 新增常见代码/配置扩展名：`.py .js .ts .java .c/.cpp .go .rs .html .css .xml .yaml .yml .toml .ini .sh .sql` 等，覆盖上传文件夹场景；二进制类型（xlsx/zip 等）仍刻意拒绝，避免乱码污染上下文。

### 3. `api/v1/uploads.py` — 新增 `POST /v1/uploads/folder`

- 请求体：`{files: [{name, relative_path, data_base64}], workspace_path | workspace_id}`
- 按 `relative_path`（浏览器的 `webkitRelativePath`）在 `<workspace>/uploads/` 下还原完整目录结构，同名覆盖（重新上传以最新为准，与图片 uuid 重命名策略刻意区分）
- 安全：`_sanitize_relative_path()` 统一 `\`→`/`、剔除 `.`、拒绝 `..` 越界 / 盘符 / 空字符；限制单文件 50MB、单请求 200 个 / 80MB
- 顺带抽出 `_resolve_upload_base()` / `_decode_file_payload()` 与图片上传共用

### 4. `api/router.py` — 注册新路由

`do_POST` 增加 `/v1/uploads/folder` 分支（仍走 90MB body 硬上限与 token 鉴权）。

### 5. `api/frontend/index.html` / `app.js` / `styles.css` — 文件夹上传交互

- composer 工具栏新增"上传文件夹"按钮（`<input webkitdirectory>`，全部主流浏览器支持）
- 选中后显示文件夹 chip（📁 名称 · 文件数 · 总大小，可移除）；`webkitRelativePath` 保留 `folder/sub/file.txt` 完整结构
- 提交时前端**分批上传**：每批 ≤30 个文件且 ≤6MB 原始字节（base64 膨胀 ~1.37x 后约 8.2MB，避开 90MB body 上限）；单文件 >50MB 跳过并计数
- 任务文本附加上下文说明：`（用户随任务上传了文件夹 "xxx"（共 N 个文件），已保存到工作空间 uploads/xxx/ 目录…）`——这是模型感知上传内容的唯一渠道
- `resetChat`/`setComposerDisabled` 同步清理与禁用新控件；静态资源版本号 `?v=20260902c` 防缓存

### 6. `prompts/system_prompt.py` / `tools/__all_tools__.py` — 注册与引导

- `ALL_TOOLS`/`TOOL_META` 新增 `write_file`、`list_files`
- 工具说明新增两条引导：面对"检查工作区/上传文件夹"任务先 `list_files` 再 `read_document`；`write_file` 被策略拒绝时不重试、改为直接输出内容

## 踩坑记录（重点）

1. **浏览器拿不到文件夹绝对路径**：`webkitdirectory` 只给相对路径，"选择本地目录作工作空间"（fs 弹层，传绝对路径）与"上传文件夹内容"（传文件落盘）是两条链路，不可混淆
2. **路径穿越双端校验**：前端 `webkitRelativePath` 本身可信，但后端不能信任任何客户端输入，`..`/盘符/绝对路径全部拒绝
3. **Windows 分隔符不一致**：落盘用 `pathlib` 自动适配 `\`，返回给模型统一 `as_posix()` 用 `/`
4. **空文件夹会消失**：浏览器 file list 不含空目录，上传后工作区无对应空目录
5. **base64 + 请求体上限**：大文件夹必须前端分批顺序上传，后端再做第二道数量/体积校验

# 修复：停止按钮（协作式取消）在多 Agent 模式下不生效

**日期**: 2026-09-02
**范围**: 取消信号链路（TaskWorker → MultiAgentOrchestrator → 子 Agent）

## 背景与问题

用户点击发送按钮（运行中变为 ⏹）后任务"停不下来"。根因：取消信号只接入了单 Agent 路径——`TaskWorker._run` 把 `should_stop` 传给了单 Agent 的 `_run_agent`，但：

1. 多 Agent 路径的 `run_role` 闭包**没有**把 `should_stop` 传给子 Agent 的 `_run_agent`；
2. `MultiAgentOrchestrator` 完全不感知取消，DAG 主循环、消融回放（每个 agent 一次完整重放）、边审计修复、评估 Agent 会**继续产生大量 LLM 调用**直到全部阶段跑完。

单 Agent 模式取消本身是通的：`graphs/loop.py` 在轮次边界、流式 chunk 之间、工具调用前三处检查 `should_stop`。

## 修改文件清单

### 1. `multiagent/orchestrator.py` — 全阶段取消守卫

- `__init__` 新增 `should_stop: Callable[[], bool] | None = None`，加 `_cancelled()` 辅助方法
- 抽出 `_drain_pending()`：把未执行的 role 标记为"未执行"（带原因与元数据，保留可诊断性）并清空队列；budget 分支同步复用，消除重复代码
- `_execute_plan` 主循环顶部：`_cancelled()` 为真 → drain 全部 pending 并 break（不再启动新 role）
- `run()` 三个后续阶段加守卫：消融回放循环（`if not self._cancelled()` 整体跳过）、边审计与修复回放（取消时返回 `[], None, []`）、评估 Agent（`enable_evaluator and not self._cancelled()`）

### 2. `api/workers.py` — 打通信号传递

- `run_role` 闭包内的 `_run_agent(...)` 补传 `should_stop=should_stop`（正在运行的子 Agent 在 chunk/轮次边界尽快退出）
- `MultiAgentOrchestrator(...)` 构造时传入 `should_stop=should_stop`（编排器停止调度新阶段）

## 设计要点（踩坑记录）

1. **协作式取消 vs 强杀线程**：Python 线程不能安全强杀，取消靠 `threading.Event` 标志 + 各循环主动轮询；代价是"停止"不是瞬时的——正在流式输出的 LLM 调用会在下一个 chunk 边界退出（秒级）
2. **多 Agent 的放大效应**：消融回放是 N 个 agent × 完整重放，不接取消信号时点一次停止可能还要跑几十次 LLM 调用，表现为"按钮没反应"
3. **事件落盘可诊断**：被取消的 role 以 `agent.completed`（`cancelled: true`）落盘而非直接消失，事后可查 DAG 执行到哪一步

## 验证方式

```powershell

# 预期：状态变"停止中" → 数秒内变"已停止"；.metamorph/runs/<id>/result.json status=cancelled
python -m pytest tests/test_agent.py -q   # 37 passed
```

# 设计总结：工作空间文件访问机制（移除文件夹上传后的最终形态）

**日期**: 2026-09-02
**定位**: 本文是当天所有工作区相关改动（新增工具 → 新增上传 → 移除上传）收敛后的最终设计说明。

## 一句话结论

**"选择文件夹"不做任何上传/复制**——它只是把本地目录登记为本轮运行的工作空间根目录，Agent 用工具**原地**读写那里的真实文件；唯一会上传复制的是**图片**（为了聊天缩略图/多模态）。

## 两条链路对比

| | 选择文件夹（底部） | 上传图片（工具栏 🖼️） |
|---|---|---|
| 是否复制文件 | **否**，原地读写 | **是**，base64 上传后写入 `<工作空间>/uploads/`（uuid 重命名） |
| 请求 | 仅 `POST /v1/tasks`（带 `workspace_path`） | 先 `POST /v1/uploads` 再 `POST /v1/tasks` |
| Agent 访问方式 | `list_files` / `read_document` / `write_file`（相对路径） | 同左；图片路径通过任务附注告知模型 |
| 覆盖语义 | 原文件直接被改 | uuid 不覆盖历史 |

## 数据流（选择文件夹）

```
① 前端 /v1/fs/list 浏览 → 确认后 selectedWsPath = "D:\work\metamorph"（底部显示 chip）
② 提交任务：body 带 workspace_path（app.js L653-654）
③ /v1/tasks → TaskWorker 把 workspace_path 存为 run 的 workspace_root
④ graphs/agent.py 给每个工具注入 ctx = {"workspace_root": ..., "allow_write": ...}
⑤ 工具内部 _resolve_within_workspace()：相对路径 → resolve() → relative_to() 校验未越界 → 原地读写
```

若不选择文件夹，则退化为 `workspace_id`（默认 `default`），实际目录 `<项目>/workspace/default/`。

## Agent 工具一览（工具层即访问层）

| 工具 | 作用 | 守门 |
|---|---|---|
| `list_files(path?, pattern?, recursive?)` | 枚举目录（扫描上限 2000 / 返回 500） | 只读 |
| `read_document(path)` | 读文本（白名单含常见代码/配置扩展名） | 只读，单文件大小上限 |
| `write_file(path, content)` | 覆盖写入并自动建父目录 | `mutates=True`，需 `METAMORPH_ALLOW_WRITE=1` |

## 安全边界与规则

1. **信任边界 = workspace_root**：三个工具统一走 `resolve()` + `relative_to()` 判定，`../`、符号链接逃逸、绝对路径全部拒绝（不能只用字符串 startswith 校验）
2. **模型只见相对路径**：列表返回 `as_posix()`，模型拼路径不受 Windows `\` 影响
3. **写权限默认关**：`allow_write=0` 时 dispatch 直接拒绝 `write_file`，提示词要求模型被拒后不重试、改为直接输出内容
4. **模型感知上传内容的唯一渠道是任务文本附注**：模型看不到 UI，图片保存位置由前端拼进 task 文本

## 常见误解澄清

- ❌ "选择文件夹 = 把文件夹上传到某处" → 实际是登记路径，零拷贝
- ❌ "Agent 改的是工作区里的副本" → 没有副本，改的就是原文件（`D:\work\metamorph` 下的文件被改就是真被改了）
- ❌ "每次任务都会上传点什么" → 不传图片时全程只有 `/v1/tasks` 一个请求
- 空目录不会出现在任何"上传"里（本就没有上传环节）；浏览器也不给网页绝对路径之外的任何文件系统权限

## 自行验证方法

1. 选定工作空间发一个任务，浏览器 DevTools Network 里应只有 `/v1/tasks`，没有 `/v1/uploads`
2. 发送"列出当前工作区的文件"→ 模型调用 `list_files`，返回的就是该目录真实结构
3. 发送"把要点写入 notes.md"（服务需 `METAMORPH_ALLOW_WRITE=1`）→ 文件直接出现在原目录

# 修复：孤儿 run 无限轮询 + 取消接口 404

**日期**: 2026-09-02
**范围**: 取消链路（`api/workers.py`）、前端轮询收敛（`api/frontend/app.js`）

## 背景与现象

用户观察到两个现象（DevTools Network）：

1. 前端对同一 run_id **反复请求** `GET /v1/runs/<id>` 和 `GET /v1/runs/<id>/events`，不停
2. 点击 ⏹ 后 `POST /v1/tasks/<id>/cancel` 返回 **404 `{"error": "not found"}`**

## 根因分析

两个现象同源：**服务重启产生"孤儿 run"**。

- 运行状态有两份：内存（`TaskWorker._cancel_flags`、工作线程）+ 磁盘（`runs.db`）。服务进程被杀时线程和取消标记消失，但磁盘状态**永远卡在 `running`**
- 前端轮询只在状态到达 `completed/passed/failed/cancelled` 终态时停止（[app.js refreshRun L481](已修)）→ 磁盘状态永不到终态 → **无限轮询**
- `cancel()` 只查内存 `_cancel_flags`：重启后字典为空 → 返回 False → 路由回 404。而磁盘上 run 看起来"还在跑"，停止按钮仍然可见可点 → **点了必 404**
- 注：轮询本身每 ~1.2s 两个请求是正常设计（运行中的 run 就该这样）；异常的是"永远不会停"

## 修改文件清单

| 文件 | 改动 |
|---|---|
| `api/workers.py` | ① `TaskWorker.__init__` 新增 `_reap_orphan_runs()`：启动时把磁盘上处于 `queued/running/cancelling` 的遗留 run 统一标记为 `cancelled`（线程已随上个进程消失，无从中断）② `cancel()` 增加孤儿兜底：内存无取消标记但磁盘 run 非终态时，直接落盘 `cancelled` 并返回 202，不再 404 |
| `api/frontend/app.js` | `refreshRun` 对 404（run 记录彻底丢失）也停止轮询并收尾，显示"运行记录丢失"，避免极端情况下的无限轮询 |

## 设计要点（踩坑记录）

1. **内存态 vs 落盘态的生命周期不一致**是此类问题的根源：凡"状态在内存、记录在磁盘"的设计，进程死亡后必须考虑磁盘残留状态的收尾（reaper 模式）
2. **取消接口对孤儿 run 应"落盘收尾"而非报错**：虽然已没有线程可中断，但把状态落盘为 `cancelled` 能让所有轮询方立即收敛，接口语义保持幂等
3. 启动收尾放在 `TaskWorker.__init__`（而非 main.py）保证无论从哪条入口启动都能生效；失败不阻塞服务启动

## 验证方式

```powershell
python -m pytest tests/test_agent.py -q   # 37 passed
# 重启后检查历史遗留 run 已被收尾：
python -c "import sqlite3; conn=sqlite3.connect('.metamorph/runs.db'); print(conn.execute('select run_id,status from runs order by created_at desc limit 5').fetchall())"
# 实测：截图中的孤儿 run 485ab0e3d233 已自动变为 cancelled，轮询停止
```

# 修复：轮询不收敛 + 刷新后状态丢失（工作空间/Agent 模式）

**日期**: 2026-09-02
**范围**: 前端轮询健壮性（`api/frontend/app.js`）、本地状态持久化

## 背景与现象

1. 任务完成后前端 Network 里 `events` / run 接口**仍反复触发**，停不下来
2. 页面刷新后，已选的工作空间路径、Agent 模式下拉框**被重置为默认值**（`default` / `单 Agent`）

## 根因分析

### 轮询不收敛（两个独立 bug）

1. **`renderEventsInto` 抛异常会阻断 `stopPolling`**：原 `refreshRun` 顺序是「渲染事件 → 判断终态 → stopPolling」，如果渲染某条结构异常的事件抛错，`stopPolling` 永远执行不到，setInterval 持续跑
2. **`loadConversationIntoChat` 终态列表漏 `cancelled`**：打开一个已取消的历史对话时，`cancelled` 不被识别为终态，会误启动轮询（虽然 `refreshRun` 里有 cancelled，但路径不一致是隐患）

### 状态丢失

1. **`loadInfo` 强制覆盖**：每次页面加载都把 `agent-mode` 设为后端 `/v1/info` 返回的默认 `mode`，覆盖用户的手动选择
2. **内存变量无持久化**：`selectedWsPath`、`workspace-input` 值都是纯内存变量，刷新即丢

## 修改文件清单

| 改动 | 说明 |
|---|---|
| `refreshRun` 重排顺序 | **先判断终态并 `stopPolling`，再 `try { renderEventsInto }`**；渲染异常被吞，不影响轮询收敛 |
| `refreshRun` 加 `cancelling` 文案 | 状态为 `cancelling` 时显示"正在停止…" |
| `loadConversationIntoChat` 终态列表 | `["completed","passed","failed"]` → 补上 `"cancelled"` |
| 新增 `lsGet/lsSet/lsRemove` 辅助 | localStorage 持久化，try/catch 兼容隐私模式 |
| `selectedWsPath` 初始化 | `lsGet(LS_WS_PATH, "")` 恢复；选择/清除时同步 `lsSet`/`lsRemove` |
| `workspace-input` | change 时 `lsSet(LS_WS_ID)`；init 时恢复 |
| `agent-mode` | change 时 `lsSet(LS_AGENT_MODE)`；`loadInfo` 优先用 localStorage 值，其次后端默认 |
| `init` 启动流程 | 先恢复工作空间 UI（`updateWsUi` + wsInput 值），再 `loadInfo` |
| 静态资源版本 | `?v=20260902e` 防缓存 |

## 设计要点（踩坑记录）

1. **轮询停止必须是"先停后渲染"**：任何可能抛异常的渲染逻辑都不能阻断 `stopPolling`，否则 setInterval 会变成永久僵尸
2. **终态列表必须全局统一**：`refreshRun` 和 `loadConversationIntoChat` 两处判断终态，容易不一致——建议后续抽成常量
3. **"用户选择"与"后端默认"的优先级**：本地持久化的用户选择应优先于后端默认值，否则刷新一次就被覆盖，持久化白做
4. **localStorage 要防隐私模式**：`setItem` 在 Safari 隐私模式下会抛异常，必须 try/catch

## 验证方式

```powershell
python -m pytest tests/test_agent.py -q   # 37 passed
# 浏览器验证：
# 1. 选 D:\work\metamorph 作工作空间、切到自适应多 Agent → F5 刷新 → 两个选择仍保留
# 2. 发一个短任务 → 完成后 Network 里 events 请求应立即停止
# 3. 打开一个已 cancelled 的历史对话 → 不会启动轮询
```

# 修复：取消接口 404 的真正根因——路由切片越界

**日期**: 2026-09-02
**范围**: `api/router.py` POST 路由匹配

## 背景

用户反复报告 `POST /v1/tasks/<id>/cancel` 返回 404，且当前对话框内任务无法停止。之前几轮修复都集中在 `TaskWorker.cancel()` 的业务逻辑（孤儿 run 兜底、幂等），但**取消接口从未真正被路由命中过**。

## 根因

[router.py L90](api/router.py#L90) 的路径切片写错：

```python
# 错误：parts[1:4] 取的是索引 1,2,3 → ["v1","tasks","<run_id>"]（3 个元素）
if len(parts) == 5 and parts[1:4] == ["v1", "tasks"] and parts[4] == "cancel":
```

对 `/v1/tasks/60a07e5bd297/cancel`，`parts = ["", "v1", "tasks", "60a07e5bd297", "cancel"]`，`parts[1:4]` 是 `["v1", "tasks", "60a07e5bd297"]`，与 `["v1", "tasks"]` 永远不等 → 条件恒假 → 直接掉到下面的 404 分支。

Python 切片 `[start:end]` 是左闭右开，`parts[1:4]` 含 3 个元素，这是经典 off-by-one。

## 修改

```python
# 正确：parts[1:3] → ["v1", "tasks"]
if len(parts) == 5 and parts[1:3] == ["v1", "tasks"] and parts[4] == "cancel":
```

## 验证

```powershell
# 直接调取消接口（run 60a07e5bd297 在 DB 里是 running 的孤儿）
curl -X POST http://127.0.0.1:8787/v1/tasks/60a07e5bd297/cancel
# → 202 {"run_id": "60a07e5bd297", "status": "cancelling"}
# DB 检查：status 变为 cancelled
python -m pytest tests/test_agent.py -q   # 37 passed
```

## 设计要点

1. **404 先查路由匹配，再查业务逻辑**：之前几轮都在改 `cancel()` 内部，但接口根本没走到那一步。遇到 404 应先用代码静态确认路由 prefix/切片/method 是否真的能命中
2. **切片越界是 Python 路由手写匹配的高发 bug**：用 `path.split("/")` 手写匹配时，切片 `[1:3]` 对应 `["v1", "tasks"]`，`[1:4]` 会多吃一个 run_id。更稳妥的写法是 `parts[1] == "v1" and parts[2] == "tasks" and parts[4] == "cancel"`，不靠切片长度

# 优化：取消立即生效 + 多 Agent 取消不显示"角色执行失败"

**日期**: 2026-09-02
**范围**: `api/workers.py`、`multiagent/orchestrator.py`、`api/frontend/app.js`

## 背景与诉求

1. 多 Agent 模式下点停止，各个 role 显示"角色执行失败"——用户认为取消不等于失败，不应展示失败
2. 无论单/多 Agent，点停止后要"立即停止"，不要等

## 修改

### 1. 取消立即落盘 `cancelled`（不等 `cancelling` 中间态）

`workers.py:cancel()`：原来设 `event.set()` 后落盘 `cancelling`，等 `_run` 自然退出再变 `cancelled`。现在**直接落盘 `cancelled`**，前端轮询立即检测到终态并停止，用户感知为"立即停止"。后台 LLM 线程仍在跑的部分结果会被丢弃（`_run` 末尾检查：若 DB 已是 `cancelled`，不允许 `completed`/`failed` 覆盖）。

### 2. 多 Agent 被取消的 role 不标记为失败

- `orchestrator.py:_drain_pending`：当 `metadata.cancelled=True` 时，`AgentResult.success=True`、`error=None`，前端不再显示"角色执行失败"
- `orchestrator.py` 主循环：正在执行的 role 完成后，若 `_cancelled()` 为 True，给 `metrics` 加 `cancelled=True`、`error=None`
- `app.js`：`agent.completed` 事件渲染时，若 `metrics.cancelled` 显示"已取消"，否则按 success 显示"已完成角色任务"/"角色执行失败"

### 3. `_run` 异常分支也尊重取消状态

`except` 分支里：若 DB 已是 `cancelled`，异常结果不记为 `failed`，保持 `cancelled`。

## 设计要点

1. **协作式取消的"立即"是感知层面的**：Python 线程不能安全强杀，`should_stop` 只能在 chunk 边界生效。但把状态**立即落盘 `cancelled`** 后，前端立即停止轮询，用户看到的就是"立即停止"。后台残留的 LLM 调用结果被丢弃，不影响最终状态
2. **取消 ≠ 失败**：用户主动停止是正常操作，不应在 UI 上展示失败态。用 `metrics.cancelled` 标志区分"被取消"和"真正失败"
3. **状态覆盖保护**：`cancel()` 先落盘 `cancelled`，`_run` 完成时必须检查当前 DB 状态，避免 `completed` 覆盖 `cancelled`

## 验证方式

```powershell
python -m pytest tests/test_agent.py -q   # 37 passed
# 浏览器：多 Agent 任务运行中点停止 → 立即显示"已停止"，各 role 显示"已取消"而非"角色执行失败"
```
