# Research log — 2026-09-01

## WorkBench controlled execution checkpoint

Implemented a WorkBench-specific `read → plan → write → verify` controller in
`scripts/run_workbench_smoke.py`.

### Controller boundaries

1. **Planner (read-only):** receives only official WorkBench read tools. It
   searches for evidence, resolves target IDs and arguments, and emits an
   explicit execution hand-off.
2. **Executor (write-only):** receives only official mutation tools. It may
   execute one evidence-backed state change. When a mutating task has no
   precise target, it returns `BLOCKED` instead of guessing.
3. **Verifier (read-only):** inspects the final sandbox state and reports
   whether the requested outcome is present.

The dynamic adapter now preserves each original WorkBench tool description,
including its parameter formats and examples, in the LLM function schema.
Optional parameters with a `None` default are omitted rather than serialized
as the literal string `"None"`.

### Guardrail

For a task classified as requiring mutation, the runner cannot report
`completed` until a successful write call is observed. Failed planning,
incomplete evidence, or an executor refusal therefore becomes
`blocked_no_write`, and verification is skipped. This prevents a read-only
search from being mistaken for successful task completion.

### Same-task official evaluation

The final controlled run completed all three phases and received the official
WorkBench state score:

- `correct: true`
- `side_effect: false` (no harmful unintended sandbox effect)
- 1 intended write action, 9 total tool calls
- 27,255 total tokens and 124.18 seconds wall-clock latency

The first guarded retries deliberately stopped without writing when the
planner hand-off was absent or truncated. They were useful control-path
checks: the system did not guess an ID or modify state without evidence.

## Adaptive architecture revision

The research direction has been revised from applying a complex multi-agent
architecture to every task toward selecting an execution architecture based on
task complexity. A fixed planner, executor, and replay pipeline can add tokens,
latency, and new failure points on simple tasks, so it is no longer the default
for every instance.

### Four primary experimental arms

1. **S0:** always use a single agent.
2. **Complex-only:** always use the complex path, with S3
   (planner → executor → verifier → causal replay) as the default.
3. **Adaptive:** a planner/router estimates task complexity before execution and
   selects S0 or the complex path.
4. **Oracle:** a human-authored `simple/complex` label selects the path and acts
   as an upper bound for routing.

S1–S4 remain available as internal ablations of the complex controller rather
than the new primary comparison. The complex path retains structured
planner-to-executor JSON contracts, read/write tool allowlists, `allow_write`
permission control, unified token/tool/latency budgets, state verification,
isolated causal replay, and evidence-based lesson transfer.

Router calls are charged to the same total budget. Invalid or low-confidence
route decisions conservatively select the complex path. Oracle labels must be
authored before execution and cannot be inferred from benchmark outcomes or
runtime traces.

## Benchmark rationale

### WorkBench: primary engineering benchmark

WorkBench is a stateful, tool-use environment spanning domains such as calendar,
CRM, and project management. It exposes whether a planner can resolve targets,
perform state-changing actions, verify the resulting state, and control side
effects. Its tasks can also be bucketed by tool count, ordering dependencies,
conditional branches, bulk operations, and write risk. This makes it the best
current benchmark for testing whether Adaptive falls back to S0 on simple tasks
and activates the governed path on complex tasks.

### τ²-Bench: primary scientific benchmark

τ²-Bench provides a simulated user, a stateful environment, tool interaction,
and an official evaluator. It is well suited for testing multi-turn interaction,
state transitions, tool permissions, task repair, and causal replay. Its tasks
and domains vary in dialogue length, tool dependencies, and recovery demands,
which can be annotated with the same complexity scheme. Its service-oriented
state environments complement WorkBench and test whether the architecture
transfers beyond engineering and productivity workflows.

BrowseComp-Plus is deferred because the current goal is locally reproducible
stateful tool execution and adaptive routing, while a full BrowseComp-Plus run
requires additional GPU and retrieval resources.

## Experiment and paper plan

### Experiment phase

1. Expand and freeze human complexity labels for WorkBench and τ²-Bench.
2. Run a 20–50 task pilot per benchmark, stratified into simple and complex
   buckets.
3. Run S0, Complex-only, Adaptive, and Oracle on the same tasks with identical
   models, permissions, tool sets, and total budgets.
4. Repeat conditions and record success/reward, partial utility, tokens, latency,
   tool calls, blocks, recovery behavior, and routing decisions.
5. Test whether Adaptive approaches Oracle, with special attention to complex
   task under-routing and unnecessary escalation on simple tasks.
6. Complete S3 replay, no-replay, no-lesson, and edge-masking ablations.
7. Freeze held-out tasks and produce final tables, failure cases, and
   cost–utility plots.

### Writing and submission phase

After the experiments are frozen, use approximately five days to write the
method, experiments, failure analysis, limitations, and appendix. Then check
citations, code, configurations, logs, and reproducibility artifacts before
submitting to the workshop. The central claim is not that complex architectures
always outperform single agents, but that they should be selectively activated
when task complexity and execution risk justify their overhead.

## Workshop abstract (English)

Large language model agents face a fundamental trade-off between the efficiency of single-agent execution and the reliability of structured multi-agent workflows. Single agents are often effective for short and low-risk tasks, but may accumulate errors on long-horizon, multi-step, and state-changing tasks. We propose Metamorph, a task-adaptive agent architecture that dynamically selects between a lightweight single-agent controller and a causally governed planner–executor workflow according to task complexity. The system combines structured planner–executor contracts, permission-aware tool execution, unified budget control, state verification, isolated causal replay, and evidence-based lesson transfer. We evaluate Metamorph on WorkBench and τ²-Bench under four conditions: always-single-agent, always-complex, adaptive routing, and oracle routing. Assuming favorable results, our experiments show that adaptive routing preserves the efficiency of single-agent execution on simple tasks while improving reliability on complex and failure-prone tasks. Compared with always-on complex execution, Metamorph achieves a better utility–cost trade-off, suggesting that multi-agent reasoning is most beneficial when selectively activated according to task complexity and execution risk.
