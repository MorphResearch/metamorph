# 研究日志 — 2026-09-01

## WorkBench 受控执行检查点

在 `scripts/run_workbench_smoke.py` 中实现了 WorkBench 专用的
`读 → 计划 → 写 → 验证` 执行控制器。

### 控制器边界

1. **Planner（只读）：** 仅获得 WorkBench 官方只读工具；检索证据、解析目标
   ID 与参数，并输出明确的执行交接计划。
2. **Executor（只写）：** 仅获得官方状态变更工具；只能执行一项有证据支撑的
   状态修改。对于需要修改状态但没有精确目标的任务，返回 `BLOCKED`，而不是猜测。
3. **Verifier（只读）：** 检查最终 sandbox 状态，并判断请求的结果是否真实存在。

动态适配层现在会把每个原始 WorkBench 工具的 description（包括参数格式和示例）
保留在 LLM 的 function schema 中。默认值为 `None` 的可选参数会被省略，不再被序列化
为字符串 `"None"`。

### 安全约束

当任务被判定为需要状态变更时，只有观察到成功的写调用，runner 才能报告
`completed`。计划失败、证据不完整或 executor 拒绝执行时，状态为
`blocked_no_write`，且跳过验证阶段。这样可以避免把只读搜索错误视为任务完成。

### 同一题的官方评测

最终受控运行完成了三个阶段，并得到 WorkBench 官方状态评分：

- `correct: true`
- `side_effect: false`（未产生有害的非预期 sandbox 副作用）
- 1 次预期写操作，9 次工具调用
- 总计 27,255 tokens，端到端墙钟延迟 124.18 秒

最初几次受控重跑在 planner 交接缺失或被截断时主动停止、没有写入。这些是有效的
控制路径检查：系统没有猜测 ID，也没有在证据不足时修改状态。

- 主项目测试套件通过：30 项测试。

## 自适应架构重构

当前研究主线从“所有任务都使用复杂 Multi-Agent 架构”调整为“根据任务复杂度
选择执行架构”。固定 planner、executor、replay 的复杂路径在简单任务上可能只会
增加 token、延迟和失败点，因此不再默认应用于全部任务。

### 四个主实验条件

1. **S0：** 始终使用单 Agent。
2. **Complex-only：** 始终使用复杂路径，默认采用 S3（planner → executor →
   verifier → causal replay）。
3. **Adaptive：** 由 planner/router 在执行前判断任务复杂度，选择 S0 或复杂路径。
4. **Oracle：** 使用实验前人工标注的 `simple/complex` 标签选择路径，作为路由上限。

S1–S4 保留为复杂控制器内部的消融条件，不再作为新的主比较条件。复杂任务路径
仍然保留以下治理机制：结构化 planner→executor JSON contract、读写工具白名单、
`allow_write` 权限、统一 token/工具/延迟预算、状态验证、隔离 causal replay 和
经验证的 lesson 迁移。

Adaptive router 的调用计入同一总预算。路由输出无效或置信度不足时，默认进入复杂
路径，避免将复杂任务错误降级为单 Agent。Oracle 标签不能根据 benchmark outcome
或运行轨迹反推。

### 当前实现

## Benchmark 选择理由

### WorkBench：主工程 benchmark

WorkBench 是状态化、工具调用型的任务环境，包含 calendar、CRM、project management
等多个工具域，适合观察 planner 是否正确解析目标、执行写操作、验证状态和控制副作用。
它也允许按任务的工具数量、顺序依赖、条件分支、批量操作和写入风险建立简单/复杂分桶，
因此最适合验证 Adaptive 是否能在简单任务上退化为 S0、在复杂任务上启用治理路径。

### τ²-Bench：主科学 benchmark

τ²-Bench 原生提供用户模拟器、状态化环境、工具交互和官方 evaluator，适合验证多轮
用户交互、状态变化、工具权限、任务修复和 causal replay 的可靠性。不同任务和 domain
具有不同的对话长度、工具依赖和恢复需求，可以进一步标注复杂度。它与 WorkBench 的
工程任务分布不同，能够检验架构是否能从代码/工作流工具迁移到服务型状态环境。

BrowseComp-Plus 暂不运行，因为当前重点是本地可复现的状态化工具执行和自适应路由，
而 BrowseComp-Plus 的完整实验需要额外 GPU 和检索资源。

## 后续实验与论文计划

### 实验阶段

1. 扩展 WorkBench 和 τ²-Bench 的人工复杂度标签，提前冻结标签规则。
2. 先完成每个 benchmark 20–50 个任务的 pilot，并按 simple/complex 分桶。
3. 对每个任务运行 S0、Complex-only、Adaptive 和 Oracle，使用相同模型、权限、工具
   集合和总预算。
4. 每个条件进行重复运行，记录 success/reward、partial utility、token、延迟、工具
   调用、阻断、错误恢复和路由决策。
5. 检查 Adaptive 是否接近 Oracle；重点分析复杂任务漏判和简单任务不必要升级。
6. 完成 S3 causal replay、no-replay、no-lesson、edge masking 等必要消融。
7. 固定 held-out 任务，生成最终表格、失败案例和成本—效用图。

### 写作与投稿阶段

实验冻结后，用约 5 天完成方法、实验、失败分析、局限性和附录，随后进行引用、代码、
配置、日志和可复现实验包检查并投稿 workshop。论文的核心结论不再是“复杂架构总是
优于单 Agent”，而是“复杂架构应在任务复杂度和执行风险足够高时被选择性启用”。

## Workshop Abstract（中文）

大型语言模型 Agent 在单 Agent 执行效率与结构化 Multi-Agent 工作流可靠性之间存在
基本权衡。单 Agent 通常适合短程、低风险任务，但在长链条、多步骤和状态变更任务中
容易累积错误。我们提出 Metamorph，一种任务自适应 Agent 架构，根据任务复杂度在轻量
级单 Agent 控制器与受因果治理的 planner–executor 工作流之间动态选择。系统结合结构化
planner–executor contract、权限感知的工具执行、统一预算控制、状态验证、隔离 causal
replay 以及基于证据的 lesson 迁移。我们在 WorkBench 和 τ²-Bench 上比较始终使用单
Agent、始终使用复杂架构、自适应路由和 Oracle 路由四种条件。假设实验结果良好，结果将
表明：自适应路由能够在简单任务上保持单 Agent 的效率，同时在复杂和易失败任务上提高
执行可靠性，并相较于始终启用复杂架构取得更好的效用—成本权衡。

## Workshop Abstract（English）

Large language model agents face a fundamental trade-off between the efficiency of single-agent execution and the reliability of structured multi-agent workflows. Single agents are often effective for short and low-risk tasks, but may accumulate errors on long-horizon, multi-step, and state-changing tasks. We propose Metamorph, a task-adaptive agent architecture that dynamically selects between a lightweight single-agent controller and a causally governed planner–executor workflow according to task complexity. The system combines structured planner–executor contracts, permission-aware tool execution, unified budget control, state verification, isolated causal replay, and evidence-based lesson transfer. We evaluate Metamorph on WorkBench and τ²-Bench under four conditions: always-single-agent, always-complex, adaptive routing, and oracle routing. Assuming favorable results, our experiments show that adaptive routing preserves the efficiency of single-agent execution on simple tasks while improving reliability on complex and failure-prone tasks. Compared with always-on complex execution, Metamorph achieves a better utility–cost trade-off, suggesting that multi-agent reasoning is most beneficial when selectively activated according to task complexity and execution risk.
