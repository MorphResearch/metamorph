# LCFM：上下文压缩边界对照实验计划

日期：2026-09-10。状态：待实现、待预注册；本文件不是已冻结的实验配置，也不授权付费运行。

## 1. 研究问题与结论边界

研究问题：在工具使用型 agent 中，按执行边界组织上下文，是否比同预算的最近历史截断更好地保留任务所需状态？其输入成本与协议交付可靠性的取舍是什么？

不是研究新 DAG、模型优劣或自动自我改进。暂定稿件标题：What Must Survive Context Compression? A Case Study of Tool-Using Agents。

旧 context_projection v1/v2/v3 日志用于提出问题，不能直接作为单变量对照。v2 原始 root 的基础设施异常与 network_retry1 的真实模型结果分开。GLM 微测试仅说明当前请求配置下的交付失败，不能证明长上下文或压缩是原因。累计 token 不等于单次上下文长度。

主实验是合成工具环境中的配对续执行实验，不是 AppWorld benchmark 结果，也不是无偏离线策略评估。给定相同初始记录、环境状态和工具，各策略随后真实调用模型、执行工具，允许轨迹分化。模拟历史须明确标记，不能冒充实际模型生成的 trace。

## 2. 预先设定的假设

- H1（主要）：在相同可见上下文上限下，边界感知策略 B 比最近历史策略 D 提高确定性任务成功率。主要对比 B−D。
- H2（次要）：B 比完整历史 A 降低输入 token；同时报告成功率差值与不确定性，不以“不显著”声称等效。
- H3（机制）：移除节点内交互的 C 比 B 更容易丢失当前节点状态或重复读取。B−C 是有意减少信息的消融，不是等信息量公平比较。

不得预设 B 必须胜出。若近期历史已足够，D 与 B 接近是合理结果。若成功率有明显损失，不只宣传 token 降幅。

## 3. 四个条件

所有条件拥有完全相同的任务要求、当前节点目标、工具 schema、权限、artifact schema、单调用输出上限、最终评分规则。工具输出均经过同一种确定性有界处理，完整结果另存审计记录。

| 条件 | 历史策略 | 用途 |
| --- | --- | --- |
| A FULL | 保留完整、合法的跨节点及当前节点历史，不额外做历史选择 | 完整信息参照 |
| B BOUNDARY | 保留直接上游合法 structured artifacts、完整有界的当前节点交互；不传播其他节点 transcript | 被检验策略 |
| C NO_LOCAL | 与 B 相同的上游 artifacts，但移除当前节点完整历史交互单元 | 机制消融 |
| D RECENT | 从完整历史池按时间保留最近完整交互单元，不做 artifact 优先选择 | 同上下文预算的简单基线 |

B 与 D 使用相同 4096-token 请求输入上限，包含共同指令和工具 schema 的统一计数。共同部分预先限制在 1024 tokens 内。若 provider tokenizer 无法获得，固定公开 tokenizer 作为预算代理，报告代理名称以及 provider 实际 input usage；不宣称精确等 provider tokens。

B 的当前节点 transcript 预先限制在 1536 代理 tokens 内，上游 artifacts 按固定依赖顺序保留。D 从同一完整记录向后装入可容纳的完整单元；不按答案或评分挑选。完整原始记录包含相同 artifacts，避免信息只对 B 开放。记录每个条件实际保留的 token、消息和证据字段；相同上限不等于实际使用量相同。

A 的输入安全上限为 32768 代理 tokens，且必须处于模型已验证的上下文窗口内；超出时记录 context_limit 并终止，不静默截断。不把窗口溢出作为研究目标。C 更短，不用随机填充凑等长。

1536-token 当前节点额度包括续执行后新增的完整交互单元。B 超出额度时按固定规则淘汰最旧完整单元；若最新必需单元单独超过额度，则记录 representation_overflow 并终止该轨迹，不拆消息、不为某条件临时扩容。C 对新增交互采用同样规则。开发集必须检查这一边界是否使所有条件无法有效执行，正式结果须单独报告该终止原因。

禁止拆散 assistant(tool_calls)→对应全部 tool results；禁止孤立 tool-result。C 删除的是完整历史单元，新产生的交互仍保留，避免人为制造无记忆死循环。B/D 不拆散多工具调用单元；结构装不下时丢弃整个单元并记录。

研究策略作用于后续工具阶段及 finalization。所有条件 finalization 使用同样 tools-disabled、JSON mode（须验证支持）、严格本地 schema、最多一次 correction retry。不能另给 C/D 一份含被删除信息的“隐藏 finalization evidence”。现有 adapter 若不把 tools=[] 实际发送到 HTTP 请求，必须准确记录实际 payload，不把抽象接口参数当已发送字段。

## 4. 样本构造和隔离

主实验：12 个模板 × 每模板 2 个独立实例 = 24 个固定案例。12 模板分成三类各四个：

1. 当前节点状态依赖：后续操作需要先前工具返回的资源 ID、分页游标或版本号。
2. 上游交接依赖：后续操作需要直接上游 artifact 中的约束、筛选条件或对象映射。
3. 近期信息充分的对照：最新完整交互已包含完成任务所需状态，压缩应无明显代价。

每模板两实例使用不同 ID/值，其中一个完整历史目标约 4K、另一个约 16K 代理 tokens。记录实际长度；使用正常任务无关交互增加距离，不仅重复无意义填充。不将此称为 128K/1M 长上下文评测。两种长度同时改变实例，不将长度差异单独解释为因果效应；长稿可增加同实例的长度配对实验。

任务目标必须可由确定性环境状态和本地断言评分。至少覆盖查询→选择→提交或查询→分页→更新等多步流程。设计者预先规定哪些操作可重读、哪些写操作非幂等、错误动作的后果，各条件一致。若环境本身暴露操作历史查询，四条件均可使用，并计入成本。

共用同一个廉价、确定性工具环境，不新建复杂 benchmark 平台。依赖标签只用于离线分析，不传给 B 策略作为答案提示。模板覆盖以上三类，避免只构造 B 擅长的“关键证据放最前面”场景。

开发集另设 6 个实例，用于检查实现、输出上限、工具可解性；不得进入主统计。24 个主案例、评分断言及任务生成器须在看主实验结果前提交并记录 hash。先用无模型的参考执行器证明全部可解，且状态隔离正常。

## 5. 协议门槛：主实验之前必须通过

候选 provider/model 沿用当前 glm-5.3；这不是兼容性已通过的声明。只允许先验证支持的请求参数并解决测量缺口，不做多模型竞赛。

在 6 个开发实例上运行：3 个 direct finalization、3 个 function continuation。统一候选输出上限 4096，显式记录实际支持的推理参数；不假定 reasoning_effort 被支持或真的发送。

进入条件：6/6 首次输出非空且可解析；最多一次 correction 后 6/6 schema-valid；全部 structured tool-call 配对正确，finish_reason 与 usage 可审计，无上下文溢出或基础设施错误。该门槛只检验可运行性，不估计普遍可靠性。

如果不通过，保留全部结果，停止主实验；一次有理由的 provider 参数修订需另存配置并重做整个开发门槛。不能无限重试到通过。兼容性验证不成功时，不以全失败的主矩阵评价压缩。

## 6. 主运行矩阵及预算

24 案例 × 4 条件 × 2 重复 = 192 条续执行轨迹。两次重复是随机性检查，不把它们视为新独立任务。若 API 支持 seed，使用 300/301 并记录；不支持则明确为重复 ID，不伪称可复现 seed。

每轨迹最多 3 个工具阶段模型请求，每阶段最多 2 次工具调用；再加一次 finalization、至多一次 correction，共最多 5 次模型请求、6 次工具调用。工具行为、执行上限在四条件间一致。每调用最多输出 4096 tokens。预算耗尽按任务失败报告，不重跑。

按案例分块，以固定随机顺序交错运行 A/B/C/D；低并发执行，记录服务波动。不得先跑全 A 再跑全 B。不以重复调用次数触发新 controller guard，否则会掩盖待测现象。

192 轨迹不是 192 请求：主实验最多 960 请求。按 A 每请求 32768、其余条件至多 4096 输入上限计算，输入容量上界约 10.82M 代理 tokens，最大输出约 3.93M tokens；开发检查和基础设施重跑另计。provider tokenizer 差异可能改变实际用量。这是容量估算，不是费用报价；预计实际用量需由开发检查估计。

正式启动前必须用所选 provider 当前价格、开发集实际用量给出美元/人民币预估，并得到用户确认的总费用上限。达到费用上限就停止，报告不完整矩阵；不挑选有利子集。若预算不足，可在主运行前将计划降为每案例 1 次重复（96 轨迹），更改预注册并说明单次局限；不能看结果后删掉第二次重复。

不同时强制各策略相同总 token 消耗，因为 A 的输入本就更贵；本实验比较相同执行机会下的效率，不声称严格等总计算预算。

## 7. 指标和统计

主要指标：确定性任务成功率；主要对比 B−D。

次要指标：首次/纠错后 schema-valid、protocol_valid、关键状态复用正确率、可避免的重复读取数、重复非幂等写入数、全部调用 input/output/total tokens、模型和本地执行延迟、纠错成本、可计算的费用。

重复调用由预注册规则识别：相同函数与规范化参数，相关环境状态未变，且不存在预定义必要轮询。分页、合理刷新、失败重试单列，不能统称浪费。

先在同案例内配对、再平均重复；置信区间按 12 个模板聚类 bootstrap。报告原始分子/分母、小样本宽区间；不以 192 当独立样本量，不以不显著推断等效。三类案例分层结果为探索性，单独标记。协议失败与能力失败均留在主要分母，不只统计 protocol-valid 子集。

空输出记录 empty；finish_reason=length 或相应服务端标志另记截断；二者可同时为真。缺失 usage 用 unknown，不用零。成本已发生但不能精确归因时报告下界/未知部分，不静默删除。

## 8. 重跑、有效性与停止规则

- 网络超时、限流等基础设施异常独立记录，最多一次追加重跑，原记录不覆盖；不混进模型成功率分母，但报告所有计划/尝试/可评分数量及总费用。
- 若无法确认工具是否执行成功，不重复非幂等动作；终止该实例并恢复到初始隔离状态后处理。
- 空输出、schema failure、错误参数、任务失败、输出上限耗尽均是模型/配置结果，不能为变好而重跑。
- 主实验出现实现错误或非法消息结构时暂停，保留整个版本；修复后使用新版本并披露，不能拼接成一次冻结实验。
- 主要结果 B 不优于 D 时，不继续改策略直到显著；允许得出简单近期历史已足够的负结果。
- 所有条件大量 empty/length failure 时先报告输出侧混淆，不归因于压缩。

## 10. 旧数据、论文和时间安排

旧 AppWorld 日志作为两个具名案例，说明如何形成假设，不用于主要因果估计。GLM 旧微测试可作为输出侧混淆的说明，不与新模型配置合并统计。

第一天：实现消息策略与确定性工具环境，补齐记录，开发门槛，冻结主案例和配置；未通过门槛则停止。
第二天：在获批费用内运行矩阵，自动生成完整表，人工审查随机案例及反例。
第三天：分析、写 4 页稿、匿名化与复现检查。运行时间只是安排，不保证在截止前完成；不能因 deadline 省略有效性检查。

成文条件：至少有干净且可解释的配对证据、一个清晰结论，以及与已有工作的实质区别。仅显示“删信息会失败”或一个消息格式 bug，不足以宣传新方法。若 B 比 D 无优势，仍可记录负结果，但是否值得投稿另行判断。

不在本计划内：新 DAG、G3 repair、P1/profile、RL、自动搜索、第二模型、全 AppWorld 矩阵、真实用户效率实验。实现本计划会新增独立实验 harness，不回写原冻结 controller。
